# Ultra: comandos web e composição server-side

Os produtos mantêm sua autenticação, titularidade, público e contas de corretora próprias. Os POST existentes no espaço de API de cada produto encaminham somente identidade autenticada e o contrato estrito para `/v1/ultra/commands`. Sem configuração e fontes autorizadas, os controles ficam indisponíveis com motivo. Nenhuma credencial foi criada ou ativada.

Start prepara um ciclo comercial de R$ 5 até a pausa confirmada. Pausa não exige um novo aceite. Apuração mensal usa o fluxo Letter existente, não confirma pagamento pelo navegador nem cria outro ledger. A política comercial prevê 20% individual e 10% quando aplicável sobre líquido geral, sem inventar isentos e sem concluir custos pendentes. Esta entrega não autoriza ordens ou débitos reais.

A fonte fornece policy.scopes.start, pause e billing como identificadores explícitos de ciclo/intenção e competência mensal, separados da revisão geral e consentVersion. A revisão geral pode mudar sem apagar uma solicitação pendente. O navegador guarda o identificador e o estado de conciliação por produto, titular e ação, independentemente de qualquer revisão. Somente uma consulta status com resultado terminal aceito, seguida de um novo scope autorizado, permite uma nova intenção. Start exige commercial_preparation conciliado; pausa exige pause_confirmed; apuração exige monthly_assessed. Resultado aceito no envio original, timeout ou revisão nova isoladamente não liberam reenvio. Rejeição stale_scope confirmada via status de recibo durável prova ausência de efeito e exige novo scope. Rejeições duráveis authority_or_consent_required ou identity_changed só permitem nova intenção após status confirmar ausência de efeito e uma política/termos/escopo novos, com novo consentimento. Outros blocked, unknown e not_found nunca liberam automaticamente a intenção. O primeiro Start/apuração envia expectedScope exatamente como autorizado pela política; o servidor compara novamente antes do efeito e inclui o escopo na deduplicação, bloqueando intenção obsoleta na virada de ciclo ou competência.

O navegador não guarda saldos, credenciais ou comprovantes, somente identidade e conciliação de solicitação em sessionStorage. O servidor precisa de commandStore durável e deduplicação comercial por ciclo/competência: o armazenamento do navegador não é garantia entre abas/dispositivos. Se o armazenamento falhar, o comando não é enviado. Sessão e política são revalidadas no retorno à página e após resultado; respostas de titular anterior são descartadas. A API rejeita proprietário, pagamento confirmado ou parâmetros financeiros fornecidos pelo cliente.

Validação sem navegador/preview: testes de controller e HTTP, verificadores históricos de fonte, tipos e build de produção. Nenhuma ordem real/testnet, pagamento, saque ou movimentação é usada para validar.
